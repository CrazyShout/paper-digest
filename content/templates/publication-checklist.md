# 简报写作与发布要求

适用于新一期简报和随附论文报告。选文细则见 [筛选规则](paper-selection-rubric.md)，正文结构见 [论文模板](paper-report-template.md) 和 [简报模板](digest-template.md)。本文件规定执行顺序、交付物和完成条件，不另维护一套正文模板。

## 开始前

- 读取上期简报及 `content/digest-audits/` 中的实际检索截止日期、未决候选和来源限制，再确定本期窗口。期号、执行时间、提交时间、版本更新时间和公告日期分别记录；时区写清楚。
- 按 `config/research-interests.json` 覆盖现有方向和优先级。通常选 5–8 篇，质量不足时减少篇数，不按方向凑数；分类边界沿用配置。
- 运行 `npm run review:preflight`。综述更新使用 `npm run review:prompt -- <direction-id>` 生成提示，并执行 [综述检查表](review-quality-checklist.md)。检查复核期限，不能用文案校订或本库检索日期代替实质复核日期。
- 记录当前提交和工作区状态；保留未完成的用户改动。收件人和凭据只存本地私有配置或 Actions Secrets；完整邮件回执只存本地私有文件或加密记录，不提交明文。

## 检索与选文

- 完整分页扫描上期采用的 arXiv 类别目录，与其 ID 快照比较；提交查询适当重叠，另查旧论文的新版本和官方资源发布。新增或遗漏类别明确记录，不能声称未查范围已覆盖。
- 结合 arXiv 元数据、正式出版源和官方项目页，尝试 Semantic Scholar、OpenAlex 补充发现。保留实际查询、端点、参数、分页、时间、返回 ID 和来源限制。访问失败或返回上限均如实记录。
- 以 DOI、arXiv ID、正式出版记录及规范化标题归并身份；原始结果保留。版本变化或代码、数据、配置、权重发布单列为更新，不重复算首次收录。
- 检索者收集证据，另一个角色筛选并说明逐项去向。区分目录出现次数、唯一 ID、范围筛查候选、去重候选、实际读过的摘要与具名原文章节；下载、解析和缓存不计作阅读。
- 入选必须有可核对的全文证据、作者单位和发表状态。正式页与预印本同时存在时保留两者；仅声明录用但缺正式页，标明录用证据的范围。

## 写作与复核

- 保持八章、公式解释、比较表、实验条件、至少两张官方图和具体跟进计划。用自然段讲问题、方法、结果与限制，不重复套用“作者主张／我的判断”标签，也不按固定比例删字。
- 短评帮助选读，正文解释机制，简报讨论补充跨论文比较。三处各有用途，不重复整篇摘要。检索过程和未执行的工作集中到来源记录；影响结论的协议差异、负结果和资源缺口仍紧邻相关结论。
- 简报末尾检索章节使用现有分段器支持的标题，如“筛选口径”或“筛选与证据口径”，并在预览中确认已经折叠。`source` 中的状态说明与 URL 用空格或 ` / ` 分隔，不能把中文括号、标点紧贴 URL；逐个核对页面实际生成的来源按钮。
- 逐项核对数字、单位、公式符号、图号、图注及资源状态。区分方法目标与测得结果、开环与闭环、非反应式回放与交互仿真、传感器匹配误差与全局定位误差；搜索得到的有限最差样本不称为数学最坏情况界。
- 相关工作比较打开各自的一手来源。没有系统查新不写“首次”，没有重复实验或统计分析不写“显著”，未测项目不写成已失败。
- 未参与撰写的审阅者核查正文、数字、比较条件及实际图片，并记录所读位置、发现、修正和结论。保留未通过轮次，不以关键词检查或 AI 分数替代语义复核。同模型家族复核注明 `same-family provisional`，不称实验复现或外部同行评审。
- 审核通过后绑定最终文件 SHA-256；正文、引用、审计或图像变化后复核受影响部分并重新绑定。综述按现有 `reviewSnapshotFingerprint` 算法排除可变审批元数据，不改算法规避失效。

## 仓库收口

- 同步简报、单篇报告、去重清单、检索审计和研究态势。每篇只在主方向显示完整条目，其他方向交叉链接；保持 ID、路径、修订关系和旧章节锚点。
- 新论文进入语料后重跑受影响综述的本库查询，核对候选与计数。保留历史站外查询及实质复核日期；只有重新检查引用与论断后才刷新 `reviewedAt`，不回填历史记录。
- Idea 中心沿用真实候选、分数和通过／淘汰／待探索状态。新一期简报不自动构成新一轮 Idea 审计。
- 公开审计只提交本期必要的来源、参数、去向、复核和指纹证据。生成物不入库；私有订阅名单、凭据和投递回执不入库。

## 验收与上线

依次运行并保留结果：

```bash
npm run review:preflight
npm run validate
npm test
TZ=UTC GITHUB_ACTIONS=true npm run build
```

- 记录实际通过、失败和因前置资产缺失而跳过的测试；跳过不写成通过。
- 在完成构建后预览正式产物，检查桌面和 390 像素窄屏的新简报、全部新增报告及修改综述：目录、原图、公式、宽表、搜索、折叠深链接、键盘操作和打印展开。不能用 HTTP 200 代替浏览器阅读检查。
- 核对论文数量、标签、引用、去重清单及审计计数，检查内部路径和锚点。正文不横向溢出；宽表与长公式可在自身容器滚动。
- 按规范、内容或代码分批提交，统一推送部署。确认 Pages 成功工作流的完整 SHA 就是最终提交。
- 部署后检查全部新增报告及修改综述，核验搜索 JSON 与 gzip 解压内容一致、官方原图和 CSS 等资源与正式构建产物一致。网络或浏览器检查失败时分别记录，不把本地结果写成线上结果。

## 邮件通知

邮件是简报更新的固定完成步骤。用户已明确授权：今后更新、生成或发布简报，均须在部署和线上核验通过后，向当前订阅者发送一次本次更新通知，无需再次询问发信许可。只有用户在当次任务明确要求不发邮件时才跳过；不能因为当次没有重复提到邮件而省略。

- 按当前本地订阅名单去重，预览既有邮件模板；短导读与具体论文条目保持简洁，链接指向已核验的线上版本。批量地址使用 BCC，不在公开文件或日志展示地址。
- 发信前按期号和本次发布版本检查回执，防止同一次更新重复发送。同一期再次更新时，通知中说明更新点，不把旧版本的回执当成本次已通知。保存发件账号、主题、消息 ID、时间、服务端响应及可取得的接受／拒收数量；接口未给出数量就记为未知，`SENT` 不等于每位收件人已送达。
- 只自动重试明确发生在投递前的 DNS、连接或认证故障。发送后状态不明确时保留回执并核查，不能盲目重发。
- 交付时分别报告网站部署状态和邮件发送状态。邮件未发送、失败或结果未知时，明确说明尚未完成通知；仅网站上线不算完成整期发布。
- `main` 部署成功后由 `Notify digest subscribers` 自动执行线上比对、内容版本去重、BCC 发送和加密回执保存。交付前确认该工作流结果；只看到 Pages 成功仍不够。`npm run email:publish -- <期号>` 也只请求同一流程，不直接旁路发信。
- 首次启用或本地订阅名单、SMTP 配置变更后，运行 `npm run email:sync-config` 同步 Actions Secrets，再发布。发送回执的解密密钥保存在忽略文件中，不随内容提交。
- 保留 `config/digest-notification-baseline.json` 的迁移历史，不重建以清空待发送版本。发送中断、部分拒收或状态未知时先核查服务商与加密回执；确认已发送后可补回执，不盲目重发。用户明确要求不发时，只对本次内容指纹记录例外。
