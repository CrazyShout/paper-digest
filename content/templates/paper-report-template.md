# 论文详细报告固定模板

这个模板用于 `content/papers/<paper-id>.md`。每篇论文都按同一套叙述骨架写，避免简报之间风格漂移。正文不要写成纯摘要，要写成可以服务选题判断、复现规划和组会讨论的阅读报告。

图片使用论文官方页面、arXiv HTML、项目页或 arXiv source/PDF 中的官方图，写成标准 Markdown 图片语法。每篇报告至少放 2 张官方图。每张图下方必须解释它在论文论证里承担的作用，避免只贴图不解读。

提交前必须逐张把图片 URL/本地文件与论文原始 figure number、caption 和正文引用对照，确认图意、编号和报告描述一致。内容校验器只能确认图片语法和本地文件存在，不能判断 `x2.png` 是否真的对应所写的“方法框架”或“结果图”；这一步必须由报告作者和独立复核者人工完成。

作者单位必须从论文 PDF 首页、arXiv source、项目页或会议页面核验后填写。不要写“作者单位见论文 PDF”“unknown”“not confirmed”这类占位；如果 arXiv API 没有单位，必须继续查 PDF/source。只有确认论文自身没有公开单位时，才在正文“局限与阅读风险”里说明，不要把占位写进 frontmatter。

如果 arXiv HTML 没有可直接引用的图片，应从官方 PDF/source 提取图并保存到：

```text
public/assets/papers/<paper-id>-figure-1.png
```

论文详情页中的相对引用写成：

```md
![图 1：一句话说明图片内容](../../assets/papers/<paper-id>-figure-1.png)
```

```md
  "comment": "两句话以内说明论文内容简介、应用场景或为什么值得读。"

## 一句话定位

用一段话回答：这篇论文属于什么问题、最核心的新意是什么、为什么进入本期。这里要给出筛选判断，而不是复述摘要。

## 论文要解决的问题

解释任务背景、已有方法的主要短板和论文切入点。要说明真实痛点，例如通信延迟、闭环评测、遮挡、鲁棒性、几何一致性、世界模型是否能服务规划等。

## 方法和系统设计

- 方法要点一：写清输入、表征或模块职责。
- 方法要点二：写清关键机制为什么解决前面的问题。
- 方法要点三：写清训练、推理或系统集成上的关键设计。

## 关键图与可视化结果

![图 1：用一句话概括图中内容，图片来源写在正文说明里](https://example.com/official-paper-figure.png)

解释这张图展示了方法结构、信息流、实验现象或定性结果中的哪一部分。说明读者应该看什么，不要只写“如下图所示”。

![图 2：如有定性结果、闭环轨迹、重建对比或 rollout，应优先放第二张](https://example.com/official-result-figure.png)

解释可视化结果支持了什么结论，以及它没有证明什么。

## 实验结论与证据

说明使用的数据集、仿真平台、指标、对比对象和最关键的证据。不要只写“效果更好”，要指出证据支持的是感知、预测、规划、鲁棒性、闭环稳定性、几何质量还是效率。

## 应用场景与启发

- 应用场景：这篇论文可能直接用于什么系统、评测或工具。
- 方法启发：它给后续选题、复现或改进留下什么具体线索。
- 讨论问题：提出一个可以在组会上推进的问题。

## 局限与阅读风险

指出论文没有证明的部分、外推风险、评测缺口、工程假设和可能的反例。高质量简报必须保留这部分，避免把论文包装成单向结论。

## 后续跟进

- 优先检查代码、数据或 benchmark 是否开放。
- 记录值得复现的最小实验。
- 明确是否需要继续跟同方向后续论文或项目页更新。
```

`tag` 保留为主方向，兼容旧内容；`tags` 用于跨方向论文。页面会把同一篇论文展示到每个匹配方向下，但详细报告文件仍只维护一份。
